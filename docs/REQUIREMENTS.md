# Grypton requirement trace

This is the implementation contract for the fork. Runtime data and the excluded
upstream `targets/` tree are not part of the fork.

| Requirement | Implementation |
|---|---|
| Fork Krypton's autonomous core without target data | `FORK_MANIFEST.json`; autonomous loop in `grypton/engine.py`; top-level `target/` stays empty; runtime lives under `.state/` |
| Kraude uses GLM 5.3 max through the Z.AI Coding Plan connector | `grypton/config.py`, `grypton/providers.py`, `grypton/worker.py`; exact route `zai-coding-plan/glm-5.3`, variant `max` |
| Kryptex uses Muse Spark 1.3 xhigh through OpenCode and the local OpenClaude gateway | `grypton/config.py`, `grypton/openclaude.py`, `grypton/providers.py`, `grypton/manager.py`; public route `go/muse-spark-1.3-contributor`, effort `xhigh` |
| Do not use OpenCode Zen or Go for Kraude | Provider-specific isolated OpenCode state in `grypton/providers.py`; worker connector contains only `zai-coding-plan` |
| Kryptex acts as the autonomous operator and resolves routine blockers | The compact manager role and `grypton/manager.py` turn context ask Spark to resolve blockers and choose Kraude's next concrete action; signature-incompatible history after a Go-key switch is retried once in a fresh, tool-disabled manager session |
| P1/P2 findings are independently validated with Astra max | Fresh tool-disabled `codex exec` process for each P1/P2 in `grypton/providers.py`; P3–P5 require `grypton validate TARGET FINDING`; exact model `gpt-6-astra`, effort `max`; a fair bounded allocator includes every explicitly referenced artifact without letting a large early capture starve later controls |
| Spark cannot validate its own worker | Manager schema requires an empty validation list; `grypton/manager.py` discards any Spark-supplied verdict and the engine accepts only Astra results |
| Persistent worker and manager context | One OpenCode session ID per role is resumed across turns and stored in `target.json`; compact role and engagement data live in the OpenCode agent prompt instead of being duplicated in every persistent user turn; each role has private XDG state |
| Continuous autonomous operation | `grypton/engine.py` runs worker → manager cycles, adding independent validation only when policy requires it, until an explicit ceiling, operator stop, binding program/scope boundary, measured convergence after one directed pivot, or unrecoverable repeated fault |
| Working `init --target` and positional target CLI | `grypton/cli.py`; both `grypton init --target HOST` and `grypton init HOST` start immediately; review commands (`show`, `findings`, `validate`, `surface`, `history`, `scope`, `audit`, `report`) and run/tool/dashboard commands are available |
| Live, fully logged terminal | Incremental OpenCode JSON parsing in `grypton/providers.py`; renderer in `grypton/chat.py`; line-buffered output works through `tee`; clean cancellable stdin handling |
| Tool errors and degenerate output are actionable | OpenCode `state.error`/`state.message` is retained when `state.output` is absent; MCP outer timeout is 120 seconds; raw events remain intact while repetitive final chatter is normalized and model previews are bounded |
| Native and structured tool calling | OpenCode native read/search tools plus the local `grypton` MCP server; Bash, write/edit, and native web tools are denied, bounded offline file inspection and literal/regex context search are exposed through `local_analyze`, every structured call is appended to `.ledger/tool-calls.jsonl`, and potentially effectful calls receive a durable pre-dispatch restart marker |
| Curl and Burp-like capture/replay | `http_request`, `proxy_flows`, `flow_read`, and `flow_replay` in `grypton/tools.py`; private bounded request/response artifacts under `flows/` |
| Private direct and rendered authentication | `credential_login` submits one scoped HTTP request; `credential_browser_login` submits one rendered form through sandboxed Chromium. Both use a private credential alias, require a same-origin verification URL, prove newly issued reusable session material against an anonymous control, share the bounded attempt state, and redact credentials and session material from every returned or persisted artifact. Browser profiles can use the existing exact-marker proof or a private status-differential proof that requires one matching submission, an exact passively observed post-login URL, material created before verification, exact live and fresh-replay authenticated statuses, and an exact fresh-anonymous 401/403 status. Redirects fail by default; a private profile may declare the anonymous control's bounded ordered redirect statuses, while every hop must remain an exact-URL GET self-redirect and live/replay remain zero-hop. A previously proven status-differential session is reused while fresh, then revalidated only against the exact verifier plus a fresh anonymous control. Exact stale proof permits one persisted credential submission per proof generation; successful renewal repeats the full proof and advances the generation, while failure restores prior material without reopening the slot. Arbitrary endpoint denials never start renewal. Maintenance stays behind the existing authentication tools and public input schemas, and safe result metadata makes its action and any credential submission observable. A denial from a later authenticated endpoint is request-specific and cannot revoke an independently proven session; denied, failed, unknown-status, and non-2xx/3xx requests atomically restore the prior cookie and token files under a per-credential lock. Credential replacement uses the same lock and atomically clears all old session and attempt material. |
| Goja TLS-fingerprint proxy | Managed `goja_start`, `goja_status`, `goja_request`, and `goja_stop`; only the recorded Grypton process may be stopped |
| Browser and reconnaissance tools | Scoped Playwright browser, ProjectDiscovery httpx, DNS, TLS certificate, bounded TCP port scan, passive subfinder, approved-documentation research fetch, inventory, fixed offline analyzers, and a curated OS-package installer |
| Strong scope controls | Exact hosts, wildcard subdomains, CIDRs, canonical URL path-subtree rules (including scheme-less host/path briefs), out-of-scope precedence, explicit URL scheme/port binding, redirect-hop protection, browser request interception, and non-URL transport separation in `grypton/tools.py` |
| Bugcrowd brief preflight | `grypton bugcrowd-brief` and `init --bugcrowd-brief` parse a saved current brief, verify the selected target, import matching scope/exclusions, expose credential and known-issue access requirements, preserve the complete normalized brief, and reject programs that prohibit automation |
| Durable attack knowledge | Append-only findings, attack-surface, tested-technique, progress, provider-call, tool-call, and flow records in `grypton/workspace.py` |
| Progress measures security novelty | Normalized request signatures, deduplicated/non-bookkeeping surface rows, passive-stagnation counters, and repetition limits in `grypton/engine.py` prevent checkpoints, hashes, and repeated requests from resetting exhaustion |
| Finding state reflects validation policy | P1/P2 start validation-pending; P3–P5 start validation-not-requested; `Workspace.set_severity_verdict` maps requested Astra results to confirmed, needs-more-evidence, rejected, or validation-pending state |
| Finding candidates meet an evidence gate | The `record_finding` MCP schema and dispatcher require title, severity, class, affected surface, impact description, reproduction, and concrete evidence; the ledger and Astra policy determine finding state |
| Minimal model prompts | Packaged role prompts and schemas live in `grypton/resources/prompts/`; explicit missions pass verbatim, the worker role adds no generated prohibitive rules, engagement data contains the recorded scope, severities, exclusions, and operator messages, and session renewal remains internal to authentication dispatch without adding prompt instructions or public MCP inputs |
| Better scenarios | Eight target-aware autonomous playbooks in `grypton/resources/autonomous_scenarios.json`, including blocker recovery, evidence handoff, and defense-aware authentication checks |
| Improved UI | Loopback-only read-only dashboard in `grypton/web.py` and `grypton/resources/web/`; live model routes, engagements, tools, flows, findings, confirmed/candidate counts, surface, tests, and verdicts |
| Reproducible review | `grypton/reporting.py` and the `audit`/`report` commands verify exact routes, provider exits, validator coverage, scope, flow integrity, and the empty target-data directory |
| Observable exact routing | Provider call records include role, route, effort, session, timing, event/tool counts, hashes, and return code without credentials |
| Offline and live verification | `tests/test_core.py`, `tests/ui_smoke.py`, and the instrumented loopback target in `grypton/local_lab.py` |

Non-negotiable invariants:

- `/root/krypton/targets` is never read or copied.
- `/root/grypton/target` remains empty.
- Kraude, Kryptex, and validator route only through the three exact models above.
- Findings remain unconfirmed until an Astra verdict is persisted; Astra is called automatically only for P1/P2.
- Numeric IDs never imply roles, and email-shaped slugs never imply real or private addresses without separate proof.
- Authentication probes stop at the first CAPTCHA, rate limit, WAF challenge, temporary block, or lockout.
- Structured network actions cannot leave the recorded host and port boundary.
- Provider credentials never appear in terminal, event, flow, or audit logs.
